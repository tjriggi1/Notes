## Summary
This session gave a five-step process for detecting and resolving project problems and explained why project performance is measured. It then covered lagging vs. leading KPIs (with burndown charts shown in class), agile velocity, lead time vs. cycle time, and information radiators (dashboards).

## Key concepts

### Problem Detection and Resolution
- Five steps in order: understand the problem (e.g. root cause analysis, brainstorming), measure it (impact on cost, scope, schedule, quality), devise a plan to manage it (with stakeholder input), resolve it, check the resolution.

### Why We Measure Project Performance
- Collecting, measuring and reporting performance information lets the team learn, facilitates decision making, helps improve some aspects of product or project performance, helps avoid issues and prevents performance deterioration.
- If performance has a problem, the resolution must be planned based on customer priorities, which are set in the requirements stage.

### Key Performance Indicator Types
- Lagging indicators: measure deliverables or milestones after they occur. Examples: percent complete, cost variance, schedule variance.
- Leading indicators: predict changes or trends before they occur. Examples: team velocity, team productivity, lead time.
- Graph shown in class: burndown charts (no image or values recorded; the table in the note is illustrative).

### Velocity Used in Agile
- Compares actual effort with estimated effort for story points; shows the average time needed to accomplish a story point compared with the estimate.

### Cycle Time and Lead Time
- Lead time includes no-value-added up-front wait time caused by the volume of work.
- Cycle time includes wait times caused by work-in-process (WIP) limits after work begins.
- Both help determine where efficiency can be improved.

### Information Radiators (Dashboards)
- Show multiple KPIs relative to each other; a project status dashboard shows key information and status in one place.

## Background (not from notes)
- These points come from the note file's "added context" sections, not from class.
- Root cause analysis finds the underlying reason, not just symptoms; verifying confirms the fix worked and caused no new problems.
- Early priorities give a rule for trade-offs (e.g. cut scope rather than delay if the deadline matters most).
- Lagging indicators confirm results but cannot prevent problems; leading indicators give early warning.
- Burndown chart: work remaining over time against an ideal line; actual above ideal means behind plan.
- Story point: relative size unit; velocity is often stated as story points completed per sprint.
- Cost variance is commonly earned value minus actual cost; schedule variance is earned value minus planned value.
- Lead time is usually measured from request to delivery, cycle time from work start to finish, so lead time is at least as long as cycle time.
- The information radiator name comes from agile practice: information posted openly (wall board or screen).
