# Project Problem Detection and Performance Measurement

*Project Mangment · 2026-11-02*

> This session covered the steps for detecting and resolving project problems, and why project performance is measured. It also covered leading and lagging indicators, agile velocity, cycle time versus lead time, and dashboards (information radiators).

## Problem Detection and Resolution

Managing a project problem follows five steps, in order: understand it, measure it, plan how to manage it, resolve it, and verify the resolution.

- Understand the problem.
    - Use techniques such as root cause analysis and brainstorming, among others.
- Measure the problem.
    - Assess its impact on cost, scope, schedule, and quality.
- Devise a plan to manage the problem.
    - Gain input from stakeholders.
- Resolve the problem.
- Check (verify) the resolution.

*Added context (not from class):*

> Root cause analysis looks for the underlying reason a problem happened, not just its symptoms. Fixing the root cause makes the problem less likely to return. Verifying the resolution confirms the fix worked and did not create new problems.

## Why We Measure Project Performance

It is important to collect, measure, and report information about project performance. If performance is experiencing a problem, the resolution has to be planned. That plan must be based on customer priorities, and those priorities must be set in the requirements stage of the project.

- Collecting, measuring, and reporting performance information is important because it does the following:
    - It enables a project team to learn.
    - It facilitates decision making.
    - It helps improve some aspects of product or project performance.
    - It helps avoid issues.
    - It prevents performance deterioration.
- If performance is experiencing a problem, it is necessary to plan the resolution.
- Planning the resolution must be based upon customer priorities.
- Priorities must be set in the requirements stage of the project.

*Added context (not from class):*

> Setting priorities early gives the team a rule for trade-offs. For example, if the customer values the deadline above extra features, the team knows to cut scope rather than delay the schedule.

## Velocity Used in Agile

Velocity is an agile measure that compares actual effort with estimated effort for story points.

- Velocity shows how much time on average is needed to accomplish a story point, compared with the time that was estimated.

*Added context (not from class):*

> A story point is a relative unit used to estimate the size of a piece of work. Velocity is more often stated as the number of story points a team completes per iteration (sprint). Teams use it to forecast how much work they can take on next. Both versions compare actual performance with the estimate.

## Cycle Time and Lead Time

Both measures track how long work takes. They differ in where the waiting time is counted.

- Lead time includes no-value-added up-front wait time caused by the volume of work.
- Cycle time includes wait times caused by work-in-process (WIP) limits after work begins.
- Both help determine where efficiency can be improved.

*Added context (not from class):*

> Lead time is usually measured from the moment a request is made until it is delivered. Cycle time is usually measured from the moment work starts until it is finished. So lead time is always at least as long as cycle time.

## Information Radiators (Dashboards)

Information radiators display project information in a form anyone can see at a glance.

- They show multiple KPIs relative to each other.
- A common type is the project status dashboard, which shows key information and status all in one place.

*Added context (not from class):*

> The name comes from agile practice. Information is posted openly, such as on a wall board or screen, so it spreads to the team and stakeholders without meetings or reports.

## Key terms

- **Root cause analysis**: A technique used to understand a problem by finding its underlying cause, not only its symptoms. The notes list it as one way to understand a problem.
- **Brainstorming**: A group technique for generating many ideas or possible causes. The notes list it as a way to understand a problem.
- **Stakeholder**: A person or group with an interest in the project or affected by it, such as the customer, sponsor, or team. Their input is gathered when planning how to manage a problem. *(added, not from class)*
- **Key performance indicator (KPI)**: A measurable value used to track how well a project is performing. KPIs are either lagging or leading. *(added, not from class)*
- **Lagging indicator**: A measure of project deliverables or milestones after they have occurred. Examples are percent complete, cost variance, and schedule variance.
- **Leading indicator**: A measure that predicts changes or trends before they occur. Examples are team velocity, team productivity, and lead time.
- **Percent complete**: A lagging indicator that shows the share of the work finished so far. *(added, not from class)*
- **Cost variance**: A lagging indicator that compares the budgeted cost of work done with the actual cost. It is commonly calculated as earned value minus actual cost. *(added, not from class)*
- **Schedule variance**: A lagging indicator that compares the work actually completed with the work planned by a point in time. It is commonly calculated as earned value minus planned value. *(added, not from class)*
- **Velocity**: An agile measure showing how much time on average is needed to accomplish a story point, compared with the time estimated. It is also commonly expressed as story points completed per iteration.
- **Story point**: A relative unit agile teams use to estimate the size or effort of a piece of work. *(added, not from class)*
- **Team productivity**: A leading indicator of how much work the team gets done over a period of time. *(added, not from class)*
- **Lead time**: The time work takes including no-value-added up-front wait time caused by the volume of work. It is a leading indicator and helps show where efficiency can be improved.
- **Cycle time**: The time work takes including wait times caused by work-in-process limits after work begins. It helps show where efficiency can be improved.
- **Work-in-process (WIP) limit**: A cap on how many tasks can be in progress at once. Work that exceeds the cap has to wait. *(added, not from class)*
- **Burndown chart**: A graph of the work remaining over time, usually compared with an ideal line, used to track progress toward completion. The teacher showed this graph in class. *(added, not from class)*
- **Information radiator (dashboard)**: A display that shows multiple KPIs relative to each other. A project status dashboard shows key information and status all in one place.

## Takeaways

- Handle problems in five steps: understand, measure (cost, scope, schedule, quality), plan with stakeholder input, resolve, and verify.
- Performance is measured so the team can learn, make decisions, improve, avoid issues, and prevent deterioration.
- Plans to resolve problems must follow customer priorities, which are set in the requirements stage.
- Lagging indicators measure what has already happened. Leading indicators predict what is coming.
- Lead time includes up-front wait time. Cycle time includes waits caused by WIP limits after work starts.
- Information radiators and dashboards show several KPIs together in one place.
